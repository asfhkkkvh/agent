想象你有一个非常聪明的朋友，他能帮你回答任何问题。

但这个朋友特别之处在于：

  📚  他们首先阅读你给他们的所有书籍和论文
      （比如你的学校课本、PDF、报告）

  🌍  如果他们在你的书中找不到答案，
      他们会替你去搜索互联网

  🤔  在他们写完答案后，第二个朋友会检查它
      并说"做得好！"或者"嘿，你漏掉了这部分，再试一次！"

  👀  第三个朋友在旁观他们的一切举动并
      做笔记 —— 所以你可以随时回去查看
      具体发生了什么

  🛠️  他们还携带一个特殊的工具箱（称为 MCP），里面有：
      - 一个知识库搜索工具（rag_search）
      - 一个实时网络搜索工具（web_search）
      - 一个完整工作流入口（full_query）
      - 一个离线评估工具（evaluate）

这就是多智能体混合系统！

用开发者的话来说：
  "一个生产级的多智能体 AI 系统，通过将混合 RAG 知识库
   与实时网络搜索相结合来回答问题，由 LangGraph 编排，
   由 LangSmith 追踪，配备 MCP 工具，并免费部署在
   Render 上。"

  🌐  （历史功能）他们曾能通过知识图谱（Neo4j）把跨页面的
      实体和关系串起来做多跳推理
      （GPT-4 → OpenAI → Microsoft 这样的关系链路）
      【已移除，仅作历史参考】

  📊  他们的回答质量用轻量评估量化打分：
      人工黄金集 + 检索 recall@k + LLM-as-judge
      （faithfulness / answer_relevancy），
      不再凭感觉评估

  🔌  除了 React 网页，他们还提供 FastAPI
      接口（REST API），方便其他程序调用：
      - /api/query   查询
      - /api/ingest  导入文档
      - /api/evaluate 跑轻量评估

问题 1：普通的 ChatGPT 不知道你的文件
--------------------------------------------------
  你有一份 200 页的公司报告。
  ChatGPT 从未见过它。
  你问"我们第三季度的收入是多少？" → ChatGPT 猜测或说"我不知道"

  多智能体混合解决方案：
  你上传你的报告 → 它阅读、学习并存储它 →
  现在它可以从你的文档中完美地回答

问题 2：AI 会编造答案（幻觉）
-----------------------------------------------
  普通 AI 有时会发明听起来真实但并非如此的事实。
  这在商业、医学、法律、金融领域很危险。

  多智能体混合解决方案：
  每个答案都由一个批判智能体检查。
  它将答案与实际来源进行比较。
  如果有错误 → 它会将答案发回修改。
  这个循环会持续到答案真正正确为止。

问题 3：AI 不知道今天的新闻
----------------------------------------
  AI 模型有一个"知识截止日期"—— 它们不知道最近的事件。

  多智能体混合解决方案：
  一个专用的网络搜索智能体使用 Tavily 来获取实时互联网结果。
  你的答案结合了你的私人文档和最新的网络信息。

问题 4：你看不到 AI 在做什么
----------------------------------------------
  普通 AI 是一个黑盒子。你问 → 它答。你不知道怎么做的。

  多智能体混合解决方案：
  LangSmith 追踪每一步：
  - 哪个智能体运行了？
  - 花了多长时间？
  - 使用了多少 token？
  - 每个智能体的输出是什么？
  全部在一个漂亮的仪表板中可见。

问题 5：构建 AI 需要花钱
------------------------------------

 第 3 部分 — 整个系统如何工作（一个问题的分步旅程）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

你输入：  "Apple 2024 年第三季度的收益是多少？"

步骤 1 — 监督智能体决定计划
  "嗯，这个问题是关于财务数据的。
   我应该同时搜索知识库和网络。"
  → 决定：两者都搜索

步骤 2 — RAG 智能体搜索你的文档
  → 接收你的问题
  → 将其转换为特殊的数字模式（嵌入：[0.2, -0.5, 0.8 ...]）
  → 使用密集搜索（基于语义）搜索 Qdrant 数据库
  → 同时使用稀疏/BM25（基于关键词，如"Q3 2024"）搜索
  → 合并两种搜索结果（倒数排名融合 RRF）
  → 双路候选 MD5 去重，运行重排序器挑选最佳的 5 个文本块
  → 找到："Apple 2024 年第三季度收入为 858 亿美元..." 来自你的 PDF

步骤 3 — 网络智能体搜索互联网
  → 向 Tavily 发送查询
  → 获取 5 个实时网络结果
  → 整理它们："据路透社报道，Apple 2024 年第三季度..."

步骤 4 — 综合智能体撰写最终答案
  → 同时获取 RAG 上下文和网络上下文
  → 撰写完整、格式化、有引用的答案
  → 包含 [RAG: apple-report.pdf/第 12 页] 和 [Web: reuters.com]

步骤 5 — 批判智能体检查答案
  → 阅读答案
  → 将每个声明与源文档进行比较
  → "所有事实均已核实。未检测到幻觉。"
  → 返回：良好 ✅

步骤 6 — 答案展示给你
  → 完整的 markdown 格式化答案
  → 包含来源引用
  → LangSmith 追踪链接，让你可以看到每个细节

整个旅程耗时：约 4-8 秒

文件 1: app/config.py  (56 行) — 设置大脑
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

它的作用：
  把它想象成一个主钥匙持有者。
  项目中的每个其他文件都向 config.py 请求密码、
  URL 和设置。它从 .env 文件读取它们，因此密钥
  永远不会被硬编码在代码中。

像五岁小孩理解的那样：
  想象你家墙上有一个规则板：
  "前门钥匙 = 门垫下面"
  "WiFi 密码 = 12345abc"
  config.py 就是那个规则板。大家都查看它。

关键代码：
  ┌─────────────────────────────────────────────────────────┐
  │  class Settings(BaseSettings):                          │
  │      zhipuai_api_key: str = Field(..., env="ZHIPUAI_API_KEY") │
  │      qdrant_url: str = Field(..., env="QDRANT_URL")     │
  │      retrieval_top_k: int = Field(10, ...)              │
  │      chunk_size: int = Field(400, ...)                 │
  └─────────────────────────────────────────────────────────┘

  第 13 行：zhipuai_api_key → 从 .env 文件读取 ZHIPUAI_API_KEY
  第 30 行：qdrant_url    → 我们在线数据库的地址
  第 36 行：retrieval_top_k = 10 → 在重排序前获取 10 个候选
  第 38 行：chunk_size = 400    → 将文档分块为 400 字符的片段（CHUNK_OVERLAP=40，按标题 header-aware 切分）

为什么重要：
  没有这个文件，每个开发者都会直接在代码中硬编码 API 密钥。
  这很危险（黑客可以从 GitHub 窃取它们）。
  pydantic-settings 也验证类型 —— 如果你在期望数字的地方
  放了一个单词，它会在启动时捕获错误。

文件 2: app/rag/ingestion.py  (217 行) — 图书管理员
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

它的作用：
  接收你的 PDF/DOCX/TXT 文件 → 阅读每个单词、表格和页面 →
  将它们分成小的文本块 → 转换为数字（嵌入）→
  存储在 Qdrant 数据库中。之后，它可以超级快速地搜索这些数字。

像五岁小孩理解的那样：
  想象你有 100 本书。你把每本书撕成小纸条
  （文本块）。你在每条纸上写一个描述它内容的
  秘密数字代码。你把所有纸条放在一个魔法盒子（Qdrant）里。
  之后，当有人提问时，盒子通过匹配数字代码找到
  正确的纸条。这就是入库！

关键函数：

  1. extract_with_docling(file_path)  [第 52-90 行]
     ┌────────────────────────────────────────────────┐
     │  converter = DocumentConverter()               │
     │  result = converter.convert(file_path)         │
     │  full_md = doc.export_to_markdown()            │
     │  pages = full_md.split("<!-- page break -->")  │
     └────────────────────────────────────────────────┘
     Docling 优先，未安装时走轻量兜底：
     - PDF → PyMuPDF（已内置，按页提取文本+表格）
     - DOCX → zipfile 标准库解析 XML（零额外依赖）
     - TXT/MD → 直接读取
     保存的元数据：源文件名、页码、内容类型

  2. get_dense_embeddings()  [第 36-40 行]
     ┌────────────────────────────────────────────────┐
     │  return ZhipuAIEmbeddings(                     │
     │      model="embedding-3"                       │
     │  )                                             │
     └────────────────────────────────────────────────┘
     使用智谱 embedding-3 将文本转换为 1024 维数字向量。
     这些数字捕捉了文本的含义。
     "猫"和"小猫"会有相似的数字模式。

  3. get_sparse_embeddings()  [第 43-45 行]
     ┌────────────────────────────────────────────────┐
     │  return SparseTextEmbedding(                   │
     │      model_name="Qdrant/bm25"                  │
     │  )                                             │
     └────────────────────────────────────────────────┘
     BM25 是经典的关键词搜索（就像旧版 Google）。
     非常适合精确术语："Q3 2024"、"EBITDA"、人名。
     新增 FastEmbedSparseAdapter 把它适配为 langchain
     Embeddings 接口（embed_documents / embed_query）。

  4. ingest_documents(documents)  [第 106-138 行]
     ┌────────────────────────────────────────────────┐
     │  # 通过 MD5 哈希去重                            │
     │  h = hashlib.md5(doc.page_content.encode())    │
     │  if h not in seen_hashes:                      │
     │      unique_docs.append(doc)                   │
     └────────────────────────────────────────────────┘
     智能去重：为每个文本块创建 MD5 指纹。
     如果你上传同一个文件两次，它不会存储重复项。
     节省资金和存储空间。

  5. ensure_collection()  [第 58-72 行]
     在 Qdrant 中创建混合集合，包含：
     - "dense" 向量（1024 维，余弦距离）
     - "sparse" 向量（BM25 关键词索引）
     两者都存在于同一个集合中以进行混合搜索。
     维度校验：若已存在集合维度不是 1024，自动删除重建。
     新增 _ensure_payload_indexes：为 source/content_type/page
     建 keyword/integer 索引（key 是 metadata.source 等嵌套路径，
     因为 langchain_qdrant 把 metadata 存在 payload.metadata.* 下）。

为什么重要：
  这是基础。没有好的入库：
  - 内容缺失 → 错误答案
  - 重复 → 浪费空间 → 搜索变慢
  - 没有元数据 → 无法按文档或页面过滤
  - 错误的文本块大小 → 太小 = 丢失上下文，
                       太大 = 用噪声淹没 AI

它的作用：

文件 16: app/rag/evaluation.py — RAGAS 评估员
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

它的作用：
  用 RAGAS 框架给 RAG 系统打"量化分数"，共 4 个指标
  （judge LLM 用智谱 GLM，与生成同模型，用于相对度量迭代效果）：
  - faithfulness（忠实性）：答案关键论断是否被检索上下文支撑（无幻觉）
  - answer_relevancy（切题性）：答案是否切题、完整覆盖问题
  - context_precision（上下文精确率）：检索上下文是否包含回答所需信息
  - context_recall（上下文召回率）：标准答案信息是否被检索到

评测集：
  人工黄金集 data/golden_set.json：人工校验的 (query, ground_truth, source)，
  不再由系统自产自销，避免自引用失真。
  报告自动保存到 data/eval_reports/eval_<时间戳>.json。

像五岁小孩理解的那样：
  LangSmith 像行车记录仪，记录每次出行但不说好坏；
  评估模块像车辆年检，给出一张可对比的评分表。
  改 prompt 或换参数后跑一次，分数涨了就是进步。

  2. run_evaluation()  [第 103 行]

启动方式：
  uvicorn app.api:app --reload --port 8000
  打开：http://localhost:8000/docs 看 OpenAPI 自动文档
  CORS 允许所有来源，方便本地前端联调。

为什么重要：
  没有它，RAG 能力只能通过网页人手操作，
  无法被自动化流水线、外部系统、自研前端调用。
  REST API 让 RAG 从"演示项目"变成"可集成的服务"。

 第 7 部分 — 关键设计概念简易解释
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

概念 1: RAG（检索增强生成）
  普通 AI："我会根据我的训练数据回答" → 可能错误/过时
  RAG AI：   "我会先搜索你的实际文档，然后回答" → 准确
  就像：开卷考试 vs. 闭卷考试。开卷总是更准确。

概念 2: 混合搜索
  仅密集   = 理解语义（"猫"匹配"小猫"） ✅
              但有时错过精确关键词 ❌
  仅稀疏   = 精确关键词匹配（"Q3 2024"） ✅
              但错过语义 ❌
  混合     = 两者通过倒数排名融合合并 ✅✅

概念 3: 多智能体系统
  单个 AI：一个大脑做所有事情 → 会困惑，会出错
  多智能体：专家团队，每个擅长一件事 → 准确结果
  就像：有专家的医院 vs. 一个做所有事的医生。

概念 4: LangGraph 状态机
  旧方法：if/else 意大利面代码 → 难以调试，难以扩展
  LangGraph：带有节点和边的可视化图 → 清晰、可扩展、可测试
  就像：流程图 vs. 一墙令人困惑的指令。

概念 5: LangSmith 可观测性
  没有它：AI 是一个黑盒子。你看到输入 → 输出。不知道发生了什么。
  有了它：每个 token、每个决定、每个工具调用都被记录并可见。
  就像：盲目飞行 vs. 拥有完整的驾驶舱仪表板。

概念 6: 自我批评循环
  AI 写答案 → AI 检查自己的答案 → AI 在需要时改进。
  这种模式称为"反思"或"宪法 AI"。
  就像：写一篇文章，然后自己校对后再提交。

概念 7: MCP（模型上下文协议）
  AI 系统共享工具的标准方式。
  就像计算机的 USB 端口 — 任何设备都能与任何计算机配合使用。
  任何支持 MCP 的 AI（Claude 等）都可以使用你的工具。

概念 8: 分块
  文档太大，AI 无法一次阅读。
  解决方案：将文档分成 400 字符的片段，带 40 字符的重叠，
  并按标题（header-aware）切分。
  重叠防止在文本块边界丢失语义。
  就像：逐章阅读一本书，每章开头提醒上一章的内容。

 第 8 部分 — 快速入门（首次设置）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

步骤 1 — 获取代码
  git clone https://github.com/asfhkkkvh/agent.git
  cd agent

步骤 2 — 获取 API 密钥（只需 4 个）
  A. 智谱 GLM:       bigmodel.cn → 控制台             → ZHIPUAI_API_KEY
  B. LangSmith:      smith.langchain.com → 设置         → LANGCHAIN_API_KEY
  C. Qdrant Cloud:   cloud.qdrant.io → 创建集群        → QDRANT_URL + QDRANT_API_KEY
  D. Tavily:         tavily.com → 仪表板                → TAVILY_API_KEY
  （无需 Neo4j：知识图谱已在 2026-09 重构中移除）

步骤 3 — 配置
  cp .env.example .env
  （打开 .env 并粘贴你的 4 个 API 密钥；
   其余参数如 CHUNK_SIZE=400 / CHUNK_OVERLAP=40 保持默认即可）

步骤 4 — 安装并运行（前后端分离）

  方式 A：React 前端 + FastAPI 后端（推荐）
  # 后端
  pip install -r requirements.txt
  uvicorn app.api:app --reload --port 8000
  # 前端（另开终端）
  cd frontend && npm install && npm run dev
  打开：http://localhost:5173（自动代理 /api 到 8000）
        http://localhost:8000/docs 看 OpenAPI 自动文档
        http://localhost:8000/api/health 看健康检查
  # 生产模式：npm run build 后，FastAPI 自动托管 frontend/dist
  直接访问 http://localhost:8000 即可

  方式 B：仅 FastAPI REST 接口
  pip install -r requirements.txt
  uvicorn app.api:app --reload --port 8000
  打开：http://localhost:8000/docs 看 OpenAPI 自动文档
        http://localhost:8000/api/health 看健康检查

步骤 5 — 上传文档并提问！
  → 网页：将你的 PDF 拖到侧边栏
        在聊天中输入"摘要要点"
        观看多智能体系统施展它的魔力 ✨
  → API：curl -F "file=@report.pdf" http://localhost:8000/api/ingest/file
        curl -X POST http://localhost:8000/api/query \
             -H "Content-Type: application/json" \
             -d '{"query":"摘要要点"}'

步骤 6 — 跑轻量评估（可选）
  → 前置：先准备人工黄金集 data/golden_set.json
  → 命令行：python -m app.rag.evaluation
  → API：  curl -X POST http://localhost:8000/api/evaluate \
               -H "Content-Type: application/json" \
               -d '{"k":10,"threshold":0.7}'
  → 输出 3 个指标：recall_at_k / faithfulness / answer_relevancy
  → 报告自动保存到 data/eval_reports/eval_<时间戳>.json
  → judge LLM 用智谱 GLM-4 有成本，离线批量跑，别高频触发
